# MIMO & HAMO — Our Little World

A private, real-time web game for two people. This first shippable version includes private two-player rooms, persisted SQLite progress, synchronized Phaser movement, real-time chat, WebRTC audio signalling and calling, six cooperative games, touch controls, and a lightweight Three.js magical forest.

## What is live in this version

- A room creator gets a non-sequential `MIMO-HAMO-XXXXXX` code and private invite URL. A room admits exactly two player identities. Reconnecting requires the local, random resume token; it does not consume another place.
- Player movement is server bounded and rate limited, then rendered smoothly for the other player. There are keyboard controls plus mobile touch controls.
- Chat, typing, room presence, memories, love points, unlocked zones, and player positions are stored in SQLite.
- **Voice call is real WebRTC audio.** The server only routes offers, answers, and ICE candidates. `getUserMedia()` runs only after the player clicks **Start voice call**; mute stops audio tracks from being sent.
- Six real, shared activities are ready: Heart Catcher, Couple Memory, Who Knows Who?, Heart Sync, Rose Garden, and Draw Together. The first Three.js level also has a server-validated cooperative Heart Crystal objective.

The next sensible increment is to build the remaining arcade games on the same server-authoritative game-event layer, then expand the Three.js adventure into its later levels. They are not presented as playable in this version.

## Local development

Prerequisite: Node.js **22.13+** (the persistence adapter uses Node's built-in SQLite support).

```powershell
Copy-Item .env.example .env
npm install
npm run dev
```

Open `http://localhost:5173` in one browser window, create a room as Hamougo, copy the invite link, and open it in an incognito window or a second browser as Mimo. This is the intended two-window test mode. `localhost` is treated as a secure context by browsers, so the microphone call can be tested locally.

Useful commands:

```powershell
npm run test
npm run build
npm start
```

`npm run build` produces `dist/client`; `npm start` serves that build and the Socket.IO service on the same origin at port 3001 by default.

## Production deployment

Deploy the Node service (not a static-only host) to Render, Railway, Fly.io, or another Node host. Set its build command to `npm ci && npm run build`, its start command to `npm start`, and provide a persistent volume for the SQLite `data/` directory. Set:

```text
NODE_ENV=production
PORT=3001
DATABASE_PATH=/persistent-volume/little-world.sqlite
CLIENT_ORIGIN=https://world.example.com
VITE_STUN_URL=stun:stun.l.google.com:19302
```

Use one public HTTPS origin for the client and Socket.IO server whenever possible; this avoids separate-origin CORS and WebSocket configuration. If the client is hosted separately (for example Vercel), deploy `dist/client` there, set its `VITE_SOCKET_URL` (after adding a custom endpoint) to the backend origin, set `CLIENT_ORIGIN` on the backend to the exact Vercel domain, and configure the host to forward WebSocket upgrades.

HTTPS is required in production for microphone permission. STUN can establish many direct calls, but a production call feature also needs a TURN server for users behind restrictive mobile networks. Use a managed TURN provider or coturn with long-term credentials, then add its URL and credentials to the `RTCPeerConnection` ICE server list using short-lived credentials generated by your backend. Do not put permanent TURN secrets in the browser bundle.

For multiple backend instances, replace the default in-memory Socket.IO adapter with the Redis adapter and migrate `Store` from SQLite to PostgreSQL. Keep validation and score calculation server-side.

## Security notes

Room codes use six characters from a restricted high-entropy alphabet and are validated server-side. This is appropriate for a private invitation prototype, but a public launch should add authenticated accounts or a signed invite-token table, expiry/revocation, CSRF/session protections if cookies are introduced, a durable rate limiter, abuse logging, and a real TURN credential service.
